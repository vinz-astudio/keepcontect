# Keep Contact 0.5.24 UX Function-Parity Design

Date: 2026-08-02  
Status: design direction approved; detailed specification awaiting human review  
Approved direction: Watch uses progressive disclosure (option A)

## Goal

Keep the prototype's warmer, calmer visual language while restoring the information and actions that make the production app useful. A redesign is complete only when every current production datum, state, and action has a visible destination or an explicit retirement decision.

## Scope

This design covers both:

1. `Prototype/interactive_prototype.html` as the directly testable UX contract.
2. The production React/Capacitor/iOS surfaces required to implement that approved contract.

Implementation will be split into bounded tasks after this specification is approved. Backend or schema changes are not assumed; if a designed field is unavailable from existing APIs, the UI must show an honest unavailable/unknown state and the missing backend capability becomes a separately governed task.

## Product principles

1. **Calm, not empty.** Reduce visual noise through hierarchy and disclosure, not by deleting decision-relevant information.
2. **Status needs evidence.** A person's state always carries recency, source class, and coverage quality.
3. **No alert is not proof of safety.** The interface says what it knows and what it cannot currently observe.
4. **Actions stay near the condition.** Concern, acknowledge, complete check-in, repair setup, and retry appear beside the state that requires them.
5. **Preferences and runtime facts stay separate.** User choices do not masquerade as OS permission, delivery, background, or evidence readiness.
6. **Privacy through abstraction.** Show evidence classes such as phone activity or manual check-in, never private phone content.

## Navigation

Retain the prototype's four primary destinations plus the centered SOS control:

- Watch
- Routine
- Circles
- Me
- SOS as a persistent emergency action, not a content tab

Alerts, check-in tasks, and recent events belong inside Watch because they answer the same question: “Does anyone need my attention now?”

## Watch information architecture

The default Watch screen has four ordered layers.

### 1. Action summary

The hero answers only the current operational question.

- With active work: `2 people need attention`, followed by counts for alerts and overdue check-ins.
- Without active work: `No active alerts right now`.
- A separate qualifier states coverage: `Evidence current for 4 of 5 people` or `1 person's coverage is limited`.
- Remove `Everything looks safe and sound`.
- Device readiness is not blended into the people-safety headline.

The summary supports loading, error, offline/stale, active, acknowledged, resolved, no-alert-with-full-coverage, and no-alert-with-limited-coverage states.

### 2. People I watch

Show every watched person, ordered by:

1. Active alert or overdue action.
2. Limited, unknown, stale, or hidden coverage.
3. Current evidence.

Each collapsed person row shows:

- Name and avatar.
- Relationship or Circle context.
- Operational state: Needs action, Limited, Unknown, or Current.
- Most recent trusted evidence age.
- Evidence source class: phone activity, manual check-in, movement available, app heartbeat, or unavailable.
- Coverage qualifier: full, partial, unavailable, hidden by privacy, or not yet established.
- A compact primary action only when appropriate, such as `View alert` or `Send concern`.

Expanding a row reveals:

- Monitoring direction: I watch them, they watch me, or reciprocal.
- Contributing devices with platform, last seen, and capability coverage.
- Recent evidence history without content details.
- Why the current state was assigned, including routine/threshold context in user language.
- Privacy restrictions and hidden evidence.
- Available actions and their pending/success/failure states.

The row must never infer a person is safe from a device heartbeat alone.

### 3. Check-in tasks

Tasks remain a separate actionable card above history.

- Show overdue, due soon, active, and pending tasks.
- Each item identifies the person, requested check-in, due time, and allowed action.
- Empty state: `No check-ins waiting`.
- Completing or sending a task exposes progress, success, failure, and retry states.

### 4. Activity history

The activity stream is supporting history, not the primary safety dashboard.

- Filters: All, Alerts, Check-ins, Evidence, and System.
- Events show person, event class, relative time, and resulting state.
- `Live` appears only when the real refresh/subscription channel is healthy; otherwise show last refresh and Retry.
- Empty and error states are explicit.

## This device and own-status placement

Watch includes a compact `My coverage` row only when the current device needs attention or the user's own evidence is stale. Full device details live in Me.

The own-status summary may say that recent routine appears usual, but must display evidence recency and `not a safety guarantee`. It links to Routine for explanation and settings.

## Onboarding

Onboarding is for an ordinary user setting up the device already in their hand. It never asks them to choose Android/iPhone/web.

Use two user tasks followed by a result screen:

1. **Understand the promise.** Brief explanation of passive signs, trusted people, privacy, and what Keep Contact cannot guarantee.
2. **Set up this device.** Auto-detect the current surface and request only capabilities that surface can actually provide. Each permission explains its benefit before invoking the real OS/app action.
3. **Result, not another task.** Run a fresh capability/evidence check using a baseline captured when verification begins. Report each capability as Ready, Limited, Needs action, or Unknown.

Rules:

- Android native, iOS native, and iOS PWA have distinct capability contracts.
- Returning from OS Settings refreshes actual permissions and app state.
- A signal from before the verification run cannot prove the new setup worked.
- Users may finish with Limited protection; the missing capability and consequence stay visible in Me and, when relevant, Watch.
- Pattern setup is a separate Me task, not an onboarding step unless it is genuinely required for the first core journey.

## Circles and responsibilities

Preserve the calmer card style while restoring:

- Community and Circle list, empty, loading, and error states.
- Create, rename, assign/move, leave, and delete operations with role-aware availability.
- Visible monitoring direction per relationship.
- Per-person routine/activity sharing and its privacy consequence.
- Invite by share link, QR generation, and QR scanning/joining.
- Invalid, expired, already-member, permission-denied, and handoff-failed invitation states.
- Guardian/ward relationships and assigned tasks in a clearly named `Responsibilities` subsection.

Emergency contacts are not a replacement for Guardians, monitoring direction, or Circle membership.

## Me

Use this order:

1. Account: name, identity, sign out, delete account.
2. Safety pattern: current status, create/change, practice, and clear.
3. This device: platform, notification delivery, passive evidence, background reliability, and last successful signal.
4. Linked devices: scan-sync, platform, version, last seen, and separate readiness per device.
5. Emergency information: encrypted crisis details, verified access path, and access explanation.
6. Updates: current version/channel, latest version, check status, and platform-appropriate update action.
7. Appearance and non-safety preferences.

Push-denied, token-registration failure, unavailable capability, stale signal, and check failure all need recovery actions. A local toggle or saved preference never produces a Ready badge by itself.

## Routine

Keep sleep window, morning grace, routine mode/sensitivity, timezone, and data-sharing consent together. Distinguish:

- What the user selected.
- What has been saved.
- What the current adaptive estimate is.
- What evidence the estimate is based on.

Provide dirty, saving, saved, failure, and rollback states. Explain unknown/outage periods rather than silently treating them as inactivity.

## SOS

- Match the production 1.4-second hold contract across pointer and keyboard input.
- Release before completion cancels.
- Delivery states are Queued locally, Accepted by server, Delivery degraded/retry, and Resolved.
- A named person is shown as having acknowledged only after a real acknowledgement receipt.
- Prototype-only simulated outcomes are visibly labelled `Demo` and can exercise success, degraded, and failure paths.
- Exact crisis location is disclosed only under the actual authorized SOS rules.

## Prototype interaction model

The prototype must let the user directly exercise:

- Watch states: normal, limited coverage, active alert, task due, loading, and error.
- Person expansion and action states.
- Event filters.
- Onboarding per auto-detected platform and capability result.
- Circle/Guardian/invite lifecycle states.
- Me permission/device/pattern/update failure and recovery states.
- Routine dirty/save/failure states.
- SOS cancellation, accepted, and degraded delivery states.

A clearly labelled prototype state switcher may provide these scenarios; it must not appear as an end-user device-selection step.

## Accessibility and visual constraints

- Preserve Warm Linen/Warm Charcoal, current typography, rounded cards, and calm semantic colors.
- Operational text and touch targets remain readable for older adults; interactive targets are at least 44 by 44 CSS pixels.
- Use semantic buttons and correctly update `aria-current`, `aria-expanded`, `aria-pressed`, dialog focus, and progress values.
- Respect reduced motion.
- Do not rely on color alone for Current, Limited, Unknown, or Needs action.
- Progressive disclosure controls must name what will open and retain keyboard focus predictably.

## Acceptance criteria

1. Every item in `docs/0.5.24-feature-coverage-audit.md` maps to a prototype and production destination or an explicit exclusion.
2. Watch shows all watched people and the collapsed-row minimum information contract.
3. Alerts and check-in tasks remain first-class and actionable.
4. No UI claims safety, readiness, live updates, delivery, expiry, or acknowledgement without corresponding runtime evidence.
5. Onboarding auto-detects the current surface and contains only two user tasks plus an honest result.
6. Circles, responsibilities, privacy sharing, invitations, and Guardians retain production functionality.
7. Me retains account, pattern, device, linked-device, emergency-information, push-recovery, and update functions.
8. Prototype state tests pass before production integration begins; production changes use TDD and platform-specific verification.

## Explicit non-decisions

- This design does not authorize a database migration, new paid service, release promotion, or weakening of accepted safety/privacy ADRs.
- Raw phone content, routine GPS history, and hidden private evidence are not added for density.
- Backend/model changes required by a missing field become separate tasks rather than being invented in the UI.

## Self-review

- The approved progressive-disclosure option is reflected in both collapsed and expanded person contracts.
- The earlier thin-Watch failure is addressed by a field/action destination matrix, not merely more sample cards.
- The user's onboarding objection is resolved through automatic surface detection and two user tasks.
- Existing production capabilities in Watch, Circles, Guardians, Me, Routine, onboarding, and SOS all have destinations.
- Safety-sensitive claims are tied to evidence and failure states.
- The specification separates reversible prototype work from production/native/backend implementation risk.
