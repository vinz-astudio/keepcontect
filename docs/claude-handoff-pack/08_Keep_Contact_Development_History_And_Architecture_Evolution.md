## 1. 项目初衷与核心价值定义

Keep Contact（简称 KC）是一套为独居群体、老人以及需要日常安全互助的亲友设计的**无感安全守护系统**。

- **核心价值**：无需主动操作，只要“正常用手机”就够了。
- **痛点反思**：市面上的签到应用通常要求用户每天定时“打卡”一次，一旦漏打卡就触发刺耳警报。这种打卡机制反人性、易遗忘，几天后用户就会嫌烦卸载，或者因为频繁误报消耗掉亲友的紧张感（消耗社会资本）。
- **终极目标形态**：长期、跨设备、隐私克制地理解每个用户与其随身设备的日常使用节奏（Usual Relationship），进而智能判断当前的沉默是否属于异常沉默（Unusually Silent）。

## 2. 阶段一：原型探索与核心漏斗成型（2026-06 ~ 2026-07）

### 2.1 漏斗机制的确立
KC 从一开始就明确：系统不是单点的“报警器”，而是一条**逐级过滤的漏斗**。
```
告活频率记录 (根基) ➔ 判断线 (触发) ➔ ①本人自证 (挡误报) ➔ ②小群 (亲友) ➔ ③社区 (互助) ➔ ④Terminal (紧急资料解锁)
```
- **第 ① 层（本人自证，Self 阶段）**：当系统判定可能异常时，**先只惊动用户本人**。
  - 核心设计：要求一个**刻意的摩擦动作**（手势 Pattern 解锁）。
  - **为什么明确排除生物识别（指纹/面容）**？因为生物识别太快，抬手就解开了。对于处于重病硬撑状态或意识不清的用户，生物识别起不到“确认人意识清醒”的作用；手势解锁是一种摩擦装置，用于消除误报并验证认知反应。
- **第 ②/③ 层（群组与社区，Group / Community 阶段）**：本人未自证，告警向外辐射到同组监护人和互助社区，推动亲友通过电话、消息主动联系。
- **第 ④ 层（终态，Terminal 阶段）**：长时间所有人均联系不上，系统才会解锁敏感的家庭地址与紧急联系人电话，以便线下上门探视或协助报警。

### 2.2 技术栈选型
- **前端**：React + Vite + TypeScript PWA（兼具 Web 访问与原生外壳封装能力）。
- **后端**：Supabase（PostgreSQL 17 + RLS 行级安全策略 + pg_cron 定时任务 + Edge Functions）。
- **底层契约**：所有安全判定、状态推进、RLS 资料权限一律由数据库函数（`SECURITY DEFINER`）严密裁决，前端只作交互呈现。

## 3. 阶段二：多端原生采集扩展与平台博弈（2026-07 ~ 2026-08）

单纯靠 Web PWA 无法实现无感知的后台被动采集，因此团队启动了跨端扩展：

### 3.1 Android 原生（Capacitor ➔ AAB / APK）
- **后台心跳与使用统计**：引入 Android `UsageStatsManager`（使用情况访问权限）和身体活动检测（`ACTIVITY_RECOGNITION`）。
- **电池优化豁免**：申请忽略电池优化（`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`），结合前台保活服务，确保在系统 Doze 模式下仍有心跳机会。
- **Google Play 合规约束**：为应对上架审核，团队制定了 `android/PLAY-CONSTRAINTS.md`，严格遵循应用商店关于显著披露（Prominent Disclosure）的规定。

### 3.2 iOS 原生（TestFlight 构建与沙盒博弈）
- **被动采集的三重约束**：
  1. 采用 HealthKit（步数、楼层更新）与 CoreMotion（运动状态）。
  2. 采用 APNs 静默推送（Silent Push）定期唤醒后台采集。
  3. **明确禁令与红线（L2 & L3）**：
     - 出货版本刻意避开 Apple 的 `DeviceActivity` / `Family Controls`（需要特殊企业审核资质）。
     - **严禁恢复 iOS 后台定位**：历史上曾短暂使用过 `UIBackgroundModes: location`，人类在 2026-08-10 明确指示彻底删除。系统必须坚持“不靠实时 GPS 追踪用户”的隐私克制承诺。

### 3.3 Windows 桌面端（Tauri）
- **托盘程序与被动报活**：通过 Windows API `GetLastInputInfo` 仅读取用户的系统空闲时长（Idle Time），绝不记录按键内容或所用软件。
- **自动更新安全**：引入 Minisign 公私钥签名机制，确保安装包与增量更新防篡改。

## 4. 阶段三：三大哲学翻转与核心重构（2026-08，最关键月份）

2026 年 8 月是 KC 架构演变最剧烈、思想最成熟的转折期。在这一个月内发生了三次重大的顶层认知翻转：

### 翻转一（ADR-0035 / ADR-0037）：抛弃固定阈值，回归账户级真实规律
- **历史困境**：早期系统设有一个全量通用的 600 分钟（10小时）死线。生产数据实测表明：不同用户的日常静默跨度相差 54 倍（有人 29 分钟，有人 26 小时）。固定的 10 小时对一半人太松，对另一半人太紧，每月制造上百次误报。
- **破局决策**：
  1. **学习是对账户的学习，不是对设备的学习**：同一账户名下多台设备合并为一个行为流，设备只负责采集上报，统合由后台完成。
  2. **不预设上下限**：人类明确否决 600 分钟天花板或硬性下限。“不去预设用户的日常频率，该什么就是什么”。
  3. **采用顶端次序统计量**：从该账户历史扣除睡眠窗的间隔中，动态计算其自身的“正常沉默上界”。证据不足时不发明阈值，诚实显示暂无判定。

### 翻转二（ADR-0038）：生产库起跑线重划（Baseline Squash）
- **历史困境**：经过数月快速迭代，仓库累积了 99 个迁移文件，很多改动曾在 Supabase 网页后台手工执行，导致仓库文件与线上账本版本号严重漂移（78 个版本对不上），本地测试全线瘫痪。
- **破局决策**：以线上真实运行的结构为唯一基准，整体导出为单一基线迁移文件（`20260808160000_baseline_from_production.sql`），历史旧迁移整体归档。确立规则：**严禁修改历史 migration 文件，后续变更一律 append-only 追加新迁移**。

### 翻转三（ADR-0039 / ADR-0040 / ADR-0043 / ADR-0044）：监测哲学大翻转
- **覆盖的四态模型（ADR-0040 修订一）**：
  必须将“用户没有动静”与“设备无法工作”严格区分开：
  - `app_foreground` / `app_background`：正常运转，可用于学习。
  - `app_killed`：App 被杀，服务器尝试唤醒并提示本人。
  - `device_off`：设备拔电、没电或断网，**记录为已知技术故障，绝对不得判为人身失联！**
- **核心监测哲学翻转（ADR-0043）**：
  **KC 停止用被动侦测取代签到，改为用被动侦测“豁免”签到！**
  - 旧网格模型（D×N）在采集器坏掉时会导致漏签滚雪球，打扰爆炸。
  - **新豁免模型**：每天只在指定时间问用户一次；如果回溯期内存在合格被动证据，则自动免除签到；就算采集器全死，最坏情况也仅仅是每天问一次，绝不给亲友发警报。
- **清醒时间滚动与精准敲门（ADR-0044）**：
  - 超时计算必须扣除用户的睡眠窗（夜间睡觉不扣减清醒超时）。
  - 超时关闭时按原因精确分类：`silent`（人无动静）、`device_unreachable`（设备不可达）、`collection_restricted`（权限关闭）。
  - 仅在截止时间前 1 小时内向可能超时的对象定向发送敲门推送（Targeted Knock），避免广播轰炸。

## 5. 阶段四：生产收敛、合规提审与告警闭环（2026-09 ~ 2026-11）

### 5.1 解锁与解除闭环（ADR-0045 · 2026-09-23）
- **历史遗留痛点**：早期曾坚持“被动活动永不解除 open 告警，必须画 pattern 解锁”。但在真实场景中，用户早上醒来看到告警通知，在手机上正常使用微信或打字，告警却依然向家属升级，造成巨大的打扰。
- **人类裁决**：
  - **一般情况下，只要检测到用户本人的合格新活动，一律自动解除告警**。
  - 仅当指定守护者明确对被特殊守护者开启了“强制 Pattern 要求”时，才在服务端进行校验。
  - 通知增加一键“确认一切安好”按钮，简化自证流程。

### 5.2 原生机制全面审查（2026-09-24）
- 审查了 iOS 0.7.8(44) 与 Android 0.7.7 的机制缺口，重点发现并修复：旧活动时间戳误标新活动、原生确认缺失告警范围绑定、离线恢复等 8 项核心问题。

### 5.3 生产 Nano 数据库卡死与 pg_cron 历史清理（2026-10-30）
- **事故现象**：生产 Postgres 无响应 45 分钟。
- **根因定位**：项目部署在 Supabase Free Nano（0.5G 内存、共享 CPU），`cron.job_run_details` 表积累了 78 万行且无清理，看门狗任务每 30 分钟全表扫描 40 遍导致超时卡死。
- **修复上线**：部署 `20261030051627` 迁移，看门狗只查最近 7 天，每日 03:47 自动清理历史日志，生产卡死问题闭环（commit `ee86410`）。

### 5.4 拔电沉默升级与终态封顶修复（2026-11-02 · 本次任务）
- **最新生产实测事实**：近 30 天 31 条沉默告警 100% 被分类为 `device_unreachable`（主因是测试 iPhone 拔电后 APNs 静默推送不唤醒）。其中 6 条一路升级到 terminal 阶段并向家属发出了解锁住址、协助报警的通知。
- **人类决策（方案 A）**：设备联系不上（`device_unreachable`）不是人身遇险，阶段升级上限**封顶在 group 或 community，严禁进入 terminal，严禁解锁家庭地址与联系人资料**。`silent` 告警维持原样。

## 6. 系统演进脉络总结与核心原则复盘

从 2026 年 6 月至今，KC 的开发过程经历了从“技术理想化”到“克制、务实、以人为本”的蜕变：

1. **对误报的认知**：误报不是单纯的“打扰”，而是对群体社会资本的不可逆损耗。每喊一次狼来了，真正的呼救就少一分希望。
2. **对平台的认知**：操作系统对后台保活的打压是必然趋势。不靠侵入式、黑客式的保活手段（如后台假定位），必须接受平台限制，并在限制下诚实降级。
3. **分层原则**：
   - 第一层（信号采集）：懂平台的差异，如实上报，不谎报健康；
   - 第二层（后台判断）：不认平台词汇，只消费归一化数据；
   - 第三层（通知分发）：严格区分设备故障与人身危险。

这就是 Keep Contact 的全部演进过程。后续的任何修复与功能演进，都必须在这一坚实的历史脉络之上继续前行。
