# 0.6.0 release runbook

Ordering is not cosmetic here. Two dependencies decide it:

- **Server before clients.** The 0.6.0 apps report coverage on channels the
  live database does not accept yet. Ship an app first and every iOS and
  desktop lease comes back `unsupported`, silently, exactly as the desktop
  shell was refused for seven days.
- **Artifacts before `version.json`.** `public/version.json` is what a running
  app reads to decide an update exists. Deploying the web build first
  advertises `keep-contact-v0.6.0.apk` at a URL that 404s.

Every step has a check that reads something outside our own code. A step that
cannot be checked has not been done.

---

## 0. Before anything

```bash
git log --oneline main..HEAD | wc -l
```

Expect 43. Then, from a clean local database:

```bash
npx supabase db reset && npx supabase test db
```

Expect `38 files, 858 tests, PASS`. This is the only thing that proves the
migration chain builds a correct database from empty, which is what the
production deploy is about to do incrementally.

## 1. Database (six migrations)

Already live: everything through `20260810030000`.

| Migration | What it changes in production |
|---|---|
| `20260809123646_s2_internal_data_api_acl_repair` | Nothing. Production already matches; this aligns the repo |
| `20260809200000_s2_..._nullable_live_comparator` | Shadow audit only — stops discarding candidate rows that have no live comparator |
| `20260810040000_s3_revert_coverage_valid_learning` | No behaviour change. Production was reverted by hand on 2026-08-10; this puts the same revert in the chain so a replay cannot resurrect it |
| `20260811000000_s3_protection_health_cycle` | **New behaviour.** A job every 30 minutes: evaluate, prompt the subject, notify their special-attention watchers after the grace period |
| `20260811010000_s3_protection_health_platform_gate` | Restricts the above to channels that can report |
| `20260811020000_s3_ios_coverage_channel` | Accepts `ios-app` / `ios-wake-v1` leases; 35-minute gap allowance; widens three table CHECK constraints |
| `20260811030000_s3_capability_is_proven_not_assumed` | Judges a platform only after it has actually produced a lease |

**Check before deploying** — simulate the first cycle read-only:

```sql
with subjects as (select distinct user_id from public.alert_observation_coverage_intervals),
sim as (
  select s.user_id,
    (select c.platform from public.clients c where c.user_id=s.user_id
      order by c.last_seen_at desc limit 1) as plat,
    (select max(i.ends_at) from public.alert_observation_coverage_intervals i
      where i.user_id=s.user_id and i.activity_coverage_state='valid'
        and i.intervention_coverage_state='valid' and i.sleep_context_state='valid') as last_valid
  from subjects s)
select coalesce(p.display_name,'?'), sim.plat,
  exists (select 1 from private.alert_shadow_coverage_leases l
           where l.user_id=sim.user_id and l.channel=sim.plat) as proven,
  case when sim.plat not in ('android-apk','tauri','ios-app')
         or not exists (select 1 from private.alert_shadow_coverage_leases l
                         where l.user_id=sim.user_id and l.channel=sim.plat)
       then 'skipped' when sim.last_valid is null
         or sim.last_valid < now()-interval '26 hours' then 'WOULD PROMPT'
       else 'healthy' end
from sim left join public.profiles p on p.id=sim.user_id;
```

Measured 2026-08-11 02:20 UTC: one healthy, one skipped, **zero prompts**. If
this shows a `WOULD PROMPT` you did not expect, stop and read why before
deploying — a prompt is a push notification to a real person.

**Check after deploying:**

```sql
select jobname, schedule, active from cron.job
where jobname = 'protection-health-cycle-v1';
select * from private.job_failures
where job_name = 'protection-health-cycle-v1' order by failed_at desc limit 5;
```

The job should exist, be active, and after the first half hour have no
failures. `select private.run_protection_health_cycle()` returns its own
counts if you want to watch one round without waiting.

## 2. Android (APK + AAB)

```bash
npm run release:android -- 0.6.0
```

This bumps `versionCode` 83 → 84, rewrites the four product version strings,
builds the web bundle, syncs Capacitor, and produces both the signed APK and
the `.aab` for Play. Artifacts land in `release-artifacts/`, never in
`public/` — an APK that gets copied into `public/` ends up packaged inside
itself, which is how a 4.7 MB build once shipped at 167 MB.

**Check:** install the APK on a real device, sign in, then

```sql
select channel, app_version, count(*), max(observed_at)
from private.alert_shadow_coverage_leases
where observed_at > now() - interval '1 hour' group by 1,2;
```

Expect `android-apk` rows at `0.6.0` within about 15 minutes.

## 3. Desktop (Tauri)

`cargo` is not on PATH in the usual shell — the desktop build needs its own
environment. Build the installer, rename it to match `exeUrl`, and place it in
`public/desktop/`.

**Check — this is the one that has never passed:**

```sql
select channel, app_version, count(*), max(observed_at)
from private.alert_shadow_coverage_leases
where channel = 'tauri' group by 1,2;
```

Zero rows have ever existed here. The shell reported itself as `desktop-web`,
so every lease it sent for seven days was refused as `capability_mismatch`
without raising an error. If this query is still empty an hour after the new
build is running, the fix did not work and the desktop side is not done.

## 4. iOS (TestFlight)

Needs a Mac. `ios/App/fastlane/Fastfile` has the `beta` lane.

The Swift added in this release **has never been compiled**. It was written on
Windows against the Android contract and reviewed by reading, which is not the
same as working. Treat the first build as a test of that code, not a formality.

**Check:**

```sql
select channel, app_version, count(*), max(observed_at)
from private.alert_shadow_coverage_leases
where channel = 'ios-app' group by 1,2;
```

Expect rows within roughly 15 minutes of the app being opened once — that is
the silent-push cadence. If HealthKit permission is granted, a walk should
produce them even after force-quitting the app, which is the property no other
iOS mechanism gives.

Then confirm the honest half:

```sql
select activity_coverage_state, count(*)
from public.alert_observation_coverage_intervals
where user_id = '<the tester>' group by 1;
```

Both `valid` and `unknown` should appear. All `valid` would mean the gap
allowance is not biting and sparse wakes are being counted as continuous
observation — the defect that produced the 2026-08-10 false alarm.

## 4b. Register the release in `app_versions` — the step that is easy to miss

Deploying artifacts does not tell anybody they exist. A signed-in client asks
`public.app_versions` first and only falls back to `version.json` when that
query returns nothing, so a release with no row is invisible to every logged-in
user no matter what the JSON says. Nothing in `release-android.mjs` writes this
row; `scripts/sync-app-version.mjs` exists for it and is easy to forget.

This was missed on 0.6.0. Everything shipped, `version.json` served 0.6.0, both
downloads returned 200 — and no client offered an update, because
`app_versions` still had 0.5.25 as the newest released row.

```bash
node scripts/sync-app-version.mjs released 0.6.0 \
  https://keep-contact-mauve.vercel.app/keep-contact-v0.6.0.apk \
  https://keep-contact-mauve.vercel.app/desktop/KeepContact-Setup.exe
```

**Check:**

```sql
select version, status, public_rollout, created_at
from public.app_versions order by created_at desc limit 3;
```

The new version must be the newest `released` row. Clients poll every 30
minutes and on focus, so an update offer should appear within half an hour.

Note that `0.6.0` against `0.5.25` is the comparison a naive check gets wrong —
`compareVersions` parses numeric segments, so 6 > 5 decides it before the 25 is
ever read. Worth re-reading whenever the minor number moves.

## 5. Web (Vercel) — last

Deploying `public/version.json` is what tells every running app that 0.6.0
exists. Do it only once the APK and the installer are actually reachable at
the URLs it names.

**Check:** fetch `https://keep-contact-mauve.vercel.app/version.json` and then
fetch the `apkUrl` it returns. A 404 there means every existing install is now
being offered a download that does not exist.

## What is not covered by any check here

- **The Swift compiles and behaves.** Only an Xcode build and a real device
  answer that.
- **Anyone's protection is actually working.** The release makes failure
  visible; it does not make coverage exist on a device whose owner has not
  installed the new build.
- **The learning layer filters its evidence.** It does not, and this release
  does not change that. Manual check-ins, Shortcut pings, Guardian
  confirmations and replayed history are all still treated as observed
  activity. See ADR-0040 revision one for what has to be built first.
